# 現状整理と再設計の起点

`DESIGN.md` は試行の時系列ログ（1700行超）なので、そこから「確定した事実」だけを
抜き出して整理し、アーキテクチャ再設計の起点とするための文書。

## 1. 評価の仕組み（シミュレータのソースから確認した一次情報）

### 1.1 fill_score は「コンテナ体積に対する割合(%)」

`src/ground_handling/evaluator.py`:

```python
fill_score = min(100 * total_item_volume / total_container_volume, 100)
```

つまり0〜100のスケール。**現状の我々のスコアは13〜19点＝コンテナ体積の13〜19%しか
埋まっていない**。ビンパッキングとしては相当低い水準であり、ここには大きな伸びしろが
あるはずだと考えるのが自然。

### 1.2 「完全に内側」でない荷物は体積が丸ごと0カウントになる

同じ `calculate_fill_rate` で、荷物の8頂点すべてについて全境界面との符号付き距離を取り、
**1つでも `> inclusion_margin` があればその荷物は体積に加算されない**（"not inside"）。

そして全ベンチ設定で `inclusion_margin = -0.005`（**負の値**）。
つまり要求は「全頂点が全境界面から **5mm以上内側**」。壁にぴったり接触（距離0）でも
アウト、4mm内側でもアウト。

境界面の構成（`utils.write_open_cut_corner_cup_obj` が返す `points`/`n_vecs`）:

| index | 内容 |
| --- | --- |
| 0〜3 | 軸方向の側壁4面 |
| 4 | 面取りされた角の斜め面 |
| 5 | 天井面（法線 +z） |
| 6 | 床面（法線 -z） |

**これは部分点ではなく全か無か**である点が重要。0.5m³の荷物が壁に1ミクロン触れただけで
0.5m³まるごと失われる。

### 1.3 荷物は「8cm上から落とされる」（積む場合のみ）

`src/ground_handling/validator.py` の `place_item`/`_transport`:

```python
resting_surfaces = [container.thickness, (container.height/2) + container.thickness + container.buffer]
bottom_z = target_pos[2] - half_lwh[2]
for r_z in resting_surfaces:
    if 0 <= (bottom_z - r_z) <= 0.05:
        effective_start_z = 0.0   # 直置き → 落下なし
        break
```

- 荷物の**底面が床面（または棚の上面）から5cm以内**なら `start_z = 0`、つまり落下なしで
  そのまま設置される。
- **それ以外（＝既存の荷物の上に積む場合）は必ず `start_z = 0.08`、8cm上から落とされる。**
- 落下後、`settle_wait_step = 300` ステップ物理を回して静定させる。

### 1.4 「配置成功」の判定は非常に緩い

`displacement_threshold = 0.3`（30cm）、`angle_displacement_threshold = 45`（45度）。
**荷物が30cm流れても「配置成功」としてカウントされる。**

### 1.5 1.2 と 1.3 と 1.4 を合わせた帰結（今回の最大の発見）

> 積み重ねた荷物は8cm落下 → 滑って最大30cmずれても「配置成功」扱い → しかし
> コンテナ境界から5mm以内まで寄ってしまうと、その荷物の体積は fill_score から
> **丸ごと除外**される。

我々のプランナーは既に軸方向の壁から12mm離して配置している（`container_state.py` の
`SAFETY_MARGIN = 0.012`）にもかかわらず、実機ログでは多数の荷物が
「壁との距離 ≈ 0（数ミクロン）」「壁から45mmはみ出し」で除外されている。
**静的なマージン設定の問題ではなく、落下・静定中のドリフトが原因**である。

しかもこの損失は **ローカルの fill_score で直接測定できる**。これまでこのセッションで
追いかけていた cog_score/stability_score（ローカルでは一切見えない）とは、この点が
決定的に違う。

### 1.5.1 損失量の実測（評価器に計測コードを差し込んで計測）

ローカルのシミュレータの `evaluator.calculate_fill_rate` に、除外された荷物の体積・
違反した面のindex・はみ出し量を出力するコードを差し込んで実測した結果:

| シナリオ | 現状のfill_score | 除外された荷物 | 除外体積 | **除外がなければ** |
| --- | --- | --- | --- | --- |
| dense_small_container_stress | 12.997 | 11個 | 0.316 m³ | **20.901** |
| shelf_container_mixed_items | 14.865 | 9個 | 0.381 m³ | **23.359** |
| タスク000 | 14.625 | 4個 | 0.420 m³ | **25.112** |
| タスク001 | 18.929 | 7個 | 0.450 m³ | **30.044** |

**平均 +9.5点（fill_score が約15 → 約25、相対+62%）。**
実際に置けている荷物の体積のうち、およそ **37%が「境界から5mm以内」という理由だけで
捨てられている**。

### 1.5.2 違反しているのは「1つの面」にほぼ集中している

`dense_small_container_stress` で除外された11個の内訳:

- **11個すべてが plane=0（＝-Y側の側壁、荷物が搬入されてくるドア側）の違反**
- うち10個は、はみ出し量が **0.00002〜0.00024 m（20〜240ミクロン）**
  ＝ 壁に「ぴったり接触」して止まっている状態
- 残り1個だけが 0.023 m の実質的なはみ出し

我々のプランナーは -Y 壁から 12mm 離して配置しているはず（`SAFETY_MARGIN = 0.012`）
なのに、最終的に壁面に接触している。**ズレ量が SAFETY_MARGIN と正確に一致する12mm**
である点が示唆的。

### 1.5.3 実際の設置は「ワープ＋静定」

`validator.place_item` は、目標位置に **直接ワープさせてから** `settle_wait_step = 300`
ステップの物理演算を回す方式。1.3 に書いた `start_z = 0.08` の落下は、その前段の
**搬入経路の衝突チェック（`_transport`）専用**であり、実際の設置は落下ではない。

したがって -Y 方向への12mmのズレは「落下による着地ズレ」ではなく、
(a) 我々が送っている目標座標が既に壁際になっている（＝座標変換のバグ）か、
(b) ワープ後の静定300ステップの間に滑って壁に到達している、
のいずれか。**現在この切り分けを実測中**（`place_item` に目標位置と最終位置を
出力するコードを差し込んで比較）。

### 1.6 最終スコアの構成

fill_score / cog_score / stability_score / placement_score / soft_item_score の加重平均。
**ローカルのサンプル評価器は fill_score と num_placed_items しか計算しない**
（他4項目はSIGNATEの本番評価基盤にしか実装がない）。

配置率（num_placed_items）は足切りにのみ使われる、というのが運営・参加者の理解。

## 2. 現アーキテクチャ（Or-optチェックポイント、実機24.407点）

```
optimize()  ... オフライン時のみ、180秒予算（実装は150秒で自己制限）
  └─ plan_order()
       ├─ 貪欲構築: 残り全アイテム × 6姿勢 × 全コンテナ から
       │    rank_placements() で最良の (item, orn, container, pos) を1つ選ぶ
       │    ＋ pick_with_lookahead(branch=2, steps=1)
       └─ _local_search_improve(): 残り時間で 2-opt swap / Or-opt relocate を
            最大2000回試行。各手は _total_order_cost() による全順序リプレイで
            検証し、厳密に改善する場合のみ採用

policy()    ... オンライン、1呼び出し8〜10秒
  └─ choose_placement() → best_position()（ハイトマップ探索）

配置スコア（selection.rank_placements）:
  score = 着地高さ top
        + 優先コンテナ違反 1000 / ソフト上積み 0.5 / 搬入経路ブロック 100
        + 不安定 100 / 角キープアウト 60
        - 0.001 * mass - 0.001 * 底面積
```

## 3. このセッションで確定した「効かないこと」

| 分類 | 試したこと | 結果 |
| --- | --- | --- |
| 構築/共有スコアリング | cog_score・placement_score向け重み強化、棚上ゾーン、重心オフセットチェック、GRASP再構築×3、層意識バイアス×3、位置レベルcog_scoreタイブレーク | **10戦全敗**。わずかな摂動で貪欲なアイテム選択順序が連鎖的に変わり、実機で予測不能に悪化 |
| 構築の作り直し | シェルフ(NFDH)方式のバッチ構築 | ローカル平均+0.56だったが実機は24.4→15.7の大幅退行。撤回 |
| 局所探索の拡張 | 焼きなまし法(SA)、ブロック移動(2〜3個同時再配置) | 実機6シナリオ全てで**完全に無変化**。既存の2-opt/Or-opt×2000回が近傍を探索し尽くしている |
| 局所探索コストへの加点 | cogタイブレーク、stabilityタイブレーク | **一度も発火しない**ことが診断で判明。実座標は連続値なので厳密な同点が起きない。重みを5000倍にしても無変化 |

### 3.1 局所探索コストへの加点が構造的に無力な理由

`_total_order_cost_detailed` の総コストは、行き詰まり（`ORDER_FAILURE_PENALTY = 100000`）
に支配される。全ベンチシナリオは「一部アイテムが入りきらない」状態で終わるため、
コスト比較は常に「何個置けたか」で決着し、cog/stability（せいぜい数十のスケール）は
比較の埒外に埋もれる。重みで解決できる問題ではない。

## 4. 評価ノイズについての現時点の理解

- 同一zipを2回提出して**小数点以下まで完全一致**したケースがある → 評価は決定的、
  またはごく低ノイズ。
- 一方で、cogタイブレークのみの版が 24.431377、そこに stability を足した版が
  **24.407109（＝タイブレーク導入前のベースラインと完全一致）** という結果になった。
  タイブレークがローカルで一度も発火しないことを踏まえると、24.431377 の方が
  説明のつかない外れ値であり、**「+0.024 は本物の改善ではなかった」**と解釈するのが
  妥当。
- 結論として、提出結果は基本的に信用してよいが、**0.02程度の差は根拠として弱い**。
  有意と見なすべきは、少なくとも0.5〜1点以上の差。

## 5. 再設計の方向性（1.5 の発見に基づく）

最大の未開拓領域は「**落下・静定中のドリフトによる体積損失をどう防ぐか**」。
これは fill_score に直結し、かつ**ローカルで直接測定・検証できる**。

検討すべき軸:

1. **壁マージンをドリフト量に見合う大きさにする**
   現状12mm。観測されているドリフトは12〜45mm。マージンを増やせば使える面積は
   減るが、「除外されて0カウント」を防げるなら差し引きプラスになりうる。
   単一定数の実験で、ローカルのfill_scoreで直接測れる。

2. **落下を伴う配置（積み上げ）と、落下しない配置（直置き）を区別する**
   `validator.py` の仕様上、**底面が床/棚から5cm以内なら落下しない**。
   つまり「落下する配置」と「しない配置」はプランナー側で完全に予測できる。
   落下する配置にだけ厚いマージンを要求する、という物理的根拠のある非対称な設計が可能。

3. **落下して滑らない配置を選ぶ**
   8cm落下しても動かないのは、平坦で十分な支持面の上に落ちる場合。現状の
   support_fraction による判定を、「落下あり」の場合だけ厳しくする。

4. **そもそも積み上げ段数を抑え、直置きできる面を増やす**
   高く積むほど落下配置が増え、ドリフトと転倒のリスクが積算される。fill_scoreは
   体積なので、低く広く敷き詰める方が有利な可能性がある。

いずれも「構築フェーズのスコアリングを変える」ことになるため、過去10戦全敗の
領域ではある。ただしこれまでの10敗は**ローカルで効果を測れない指標（cog_score等）を
狙ったもの**で、今回は**ローカルのfill_scoreで直接測れる**点が決定的に違う。
測定しながら進められるので、同じ轍は踏まない。
