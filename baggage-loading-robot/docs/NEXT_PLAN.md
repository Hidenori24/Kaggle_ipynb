# 次の一手の計画

Public スコアの返却を待つ間に整理した、次に試す施策の優先順位と手順。

## 0. 現在地と、ローカル→本番の換算率

| 版 | ローカル平均fill_score | 実機Publicスコア |
| --- | --- | --- |
| Or-optチェックポイント | 14.158 | 24.407109 |
| 床置きペナルティ（現行） | 17.123 | **25.042818** |

差分は ローカル **+2.965** に対し 本番 **+0.636**。比率 **0.214**。

最終スコアは fill_score / cog_score / stability_score / placement_score /
soft_item_score の加重平均であり、この比率は**5項目のほぼ等加重平均**
（1/5 = 0.2）と整合する。したがって:

> **ローカルのfill_score +1点 ≈ 本番の総合スコア +0.2点**

この換算率があるので、今後は**提出前にローカルで期待値を見積もれる**。
（cog/stability等を動かす施策には適用できない点に注意。あくまで
fill_score を動かす施策の換算率。）

## 1. 残っている伸びしろ（最優先）

現行版でも、置けている荷物のうちかなりの体積が「境界から5mm以内」で
除外され続けている:

| シナリオ | 現在のfill | 除外ゼロなら | 残りの伸びしろ |
| --- | --- | --- | --- |
| dense_small_container_stress | 12.997 | 20.901 | +7.9 |
| shelf_container_mixed_items | 15.535 | 23.359 | +7.8 |
| single_container_online_large_items | 19.478 | 28.451 | +9.0 |
| two_containers_online_heavy_soft | 14.913 | 22.214 | +7.3 |
| タスク000 | 21.272 | 30.753 | +9.5 |
| タスク001 | 18.545 | 26.335 | +7.8 |
| **平均** | **17.123** | **25.336** | **+8.2** |

換算率0.214を当てると、**全部回収できれば本番 +1.75点（≒26.8点）**。
これが現実的な上限の目安。

### 1.1 【測定済み】残りの除外は 100% が最下層

面ごとの内訳を実測した結果（3シナリオ）:

| シナリオ | 床面違反 | 壁・天井・面取り |
| --- | --- | --- |
| dense_small_container_stress | 11個 0.3161 m³ | **0** |
| single_container_online_large_items | 4個 0.2718 m³ | **0** |
| タスク000 | 4個 0.3799 m³ | **0** |

**壁・天井・面取り面での除外は1件もない。** → 計画のB系（壁・天井マージンの
見直し）は不要と確定。

なお、床面違反のうち一部は「床に接地していない」ように見えるが、詳しく見ると
ソフト貨物（`contactStiffness` が設定された荷物）が**柔らかい接触で床に
めり込み**、底面頂点が床面より下に沈んだものだった（例: `dense_small` の
item 35 は中心が床から80mmなのに最小半径が99mm、落下量も通常の37mmではなく
56mm）。**これらも実質的に最下層の荷物**である。

したがって **残る伸びしろ +8.2点は、全て「最下層の体積」**。
唯一のレバーは**最下層に置く荷物の体積を小さくすること**（＝A系）。

## 1.2 【最重要】1回の配置失敗でエピソード全体が即終了する

`src/ground_handling/env.py` の `step()`:

```python
is_included = self.validator.check_inclusion(...)
if not is_included:
    terminated = True                    # ← 終了
else:
    is_valid = self.validator.check_transport_path(...)
    if is_valid:
        is_placed_safe = self.validator.place_item(...)
        if is_placed_safe:
            ...成功...
        else:
            terminated = True            # ← 終了
    else:
        terminated = True                # ← 終了
```

失敗の経路は3つ（内包判定・搬入経路・着地後の安定性）で、**どれか1つでも
失敗した時点でエピソードが終わり、残りの荷物は全て失われる**。

実測の配置率は平均53%（38〜78%）。つまり**半分の荷物は、積めなかったのではなく
「その前にエピソードが終わったから積む機会が無かった」**。
`only_000` の実ログでは
`Not safe place (disp: 0.78m, angle: 96.3deg). Item 22 removed.`
という転倒1件で、41個中16個を積んだところで打ち切られていた。

### この事実が意味すること

- **失敗を1回避けることの価値 = 残り全部の荷物の体積**であり、
  「1個の荷物の価値」ではない。
- 現在のスコアリングは危険な配置に `UNSTABLE_PENALTY = 100` を課しているが、
  真のコストはこれより大きい場面がある。
- したがって**安全側に倒す方が期待値が高い**可能性が高い。fill_score は
  「置けた体積」なので、1個分の体積を諦めて残り20個を守れるなら大幅なプラス。
- しかも配置率が上がれば段数が増え、**最下層が積載体積に占める割合が下がる**ため、
  1.1 で特定した「最下層の無駄」も相対的に小さくなる。二重に効く。

**→ 検証中**: 安定性の要求値 `MIN_SUPPORT_FRACTION`（現行0.6）/
`MIN_CORE_SUPPORT_FRACTION`（現行0.5）を厳しくするスイープ
（0.7/0.6 と 0.8/0.7）。

## 2. 施策候補（測定結果を待って優先順位を確定）

### A. 床層の体積をさらに削る（床ペナルティの強化・拡張）

現行 `FLOOR_WASTE_WEIGHT = 1.0`。まだ床層に体積が残っているなら:

- **A-1. 重みのスイープ → 実施済み。現行1.0が鋭い局所最適、変更なし**

  | | W=0.5 | **W=1.0（現行）** | W=2.0 |
  | --- | --- | --- | --- |
  | 平均fill_score | 11.39 | **17.12** | 13以下 |

  W=0.5 は床ペナルティ無し（14.16）よりさらに悪いという非単調な結果。
  ここから分かるのは、**効いているのは「平たい荷物を床に選ぶ」ことではなく
  「床に置くか上に積むかのトレードオフ」の方**だということ（床置き候補同士の
  並び順は `W * dh` なので重みの大きさに依らず不変）。実質的に**荷物を上へ
  押し上げる力**として機能しており、1.0がちょうど良い強さだった。
- **A-2. `dh` ではなく「体積 ÷ 支持有効面積」で評価する**。現在は高さのみで
  評価しているが、実際には「その荷物が土台としてどれだけの面積を提供するか」
  も効く。面取り部にはみ出す荷物などは有効面積が小さい。
- **A-3. オフラインプランナーの順序生成にも、壊さない形で反映する**。
  現在は `floor_waste=False` で完全に切っている。順序の生成規則
  （`largest_first_order`）自体を「最初のN個だけ平たい順」にするなど、
  構築のスコアリングを変えずに順序だけ変える方法なら、過去10敗の
  「スコアリング摂動」とは別物になりうる。ただしリスクは高め。

### B. 壁・天井での除外を潰す → **不要と確定（1.1 参照）**

実測の結果、壁・天井・面取り面での除外は1件も無かったため、この系統は
追わない。現行の `SAFETY_MARGIN = 0.012` / `top_margin = 0.02` は
5mm要求に対して十分に効いている。

### C. `LANDING_CLEARANCE = 0.025` の見直し → **短縮不可と確定**

0.010 に下げたところ、ほぼ全シナリオが全滅した（fill_score 0.72 / 1.28、
複数シナリオは配置ゼロ）。原因は `validator.py` の搬入経路チェックが
`safety_margin = 0.015`（15mm）以内に他の物体があると「配置不可」と
判定するため。**25mm のうち 15mm は検証側が要求する必須クリアランス**であり、
無駄ではなかった。現行値は妥当。

### D. もっと高く積む方向へ寄せる

カウントされるのは床より上の体積だけなので、**上へ積むほど有利**。
現行スコアは `top`（着地高さ）の最小化＝「低く置く」を志向しており、
真の目的と部分的に対立している。ただしここを直接触るのは
構築フェーズの摂動そのもの（過去10敗の領域）なので、**Cで段数を稼ぐ方が
安全**。Cが効かなかった場合の次善策とする。

## 3. 進め方（Public到着後に即実行できる形）

1. 面ごとの内訳測定の結果を見て、**A系 か B系 か**を決める
2. 決めた系統で**最も単純な定数スイープ**から着手（A-1 または B-1/B-2 または C）
   - いずれもローカル6シナリオで直接測定できる
   - 換算率0.214で本番への効果を事前に見積もる
3. ローカルで **+1.0 以上**（＝本番 +0.2以上）の改善が出たものだけ提出する
   - 0.02程度の差は根拠として弱い、というのが今セッションの教訓
4. 提出は1回につき1つの変更だけにする（今回の「全面適用 vs 分離」のように、
   効いた理由を切り分けられる形を保つ）

## 4. やらないこと（このセッションで否定済み）

- cog_score / stability_score / placement_score 狙いのタイブレーク項
  → 実データで一度も発火しない。重みを5000倍にしても無変化（構造的に無力）
- 局所探索フェーズの拡張（SA、ブロック移動など）
  → 既存の2-opt/Or-opt×2000回が近傍を探索し尽くしており、実機で完全に無変化
- 構築フェーズ（`rank_placements`）のスコアリングへの摂動
  → 10戦全敗。今回の床ペナルティも、全面適用した1段階目は同じ形で失敗した
  （オンライン側に限定して初めて効いた）

### L字搬入経路の顛末（仮説は外れ）

`check_transport_path` が搬入開始Xを面取り分だけクランプし、深い位置の
荷物は「入口までY方向 → そこから横移動」というL字経路で運ばれる、という
仕様自体は実在した（`cut_x` は `dense_small` で2.17mのうち0.533m）。
我々のモデルはこの横移動を見ておらず、コメントにも
"travel straight up the Y axis at roughly a fixed X" と明記されていた。

そこで横移動の経路もチェックするよう修正したが、実機では
**6シナリオ中5つが完全に無変化、タスク000のみ -3.65**。しかも
`not packable` による打ち切りは修正後も同じように発生し続けた
（`dense_small` item 52、`shelf` item 6、タスク001 item 22）。

つまり**L字経路は仕様としては実在するが、実際の打ち切り原因ではなかった**。
保守的な判定が有効な配置を減らした分だけ悪化した。撤回。

### 現時点の整理

- 配置率（平均53%）を上げることが最大のレバーである、という 1.2 の分析は変わらない
- ただし「安定性を厳しくする」「搬入経路を厳密にモデル化する」という
  2つの直接的なアプローチはどちらも失敗した
- `not packable` の真の原因はまだ特定できていない。次に進むなら、
  **失敗した瞬間の目標位置と周辺の実際の配置状態をダンプして、
  検証コードの判定と我々のモデルの判定がどこで食い違うのかを1件ずつ突き合わせる**
  必要がある（推測ベースの修正は2回とも外れた）

## 6. 危険な配置より安全な配置を優先する（採用、ローカル無変化だが実機提出）

診断（1.2）の結論を受け、`best_position`に`require_safe`モードを追加した。
経路・安定性・面取りキープアウトを全てクリアする配置だけを対象にし、
無ければ`None`を返す。`policy.py`は毎回、まず安全な配置だけでプール全体を
探索し、プール内のどのアイテムにも安全な配置が無い場合にのみ、従来の
「最もマシな危険な配置」にフォールバックする。オンライン側のみの変更で、
構築フェーズ・オフラインプランナーには触れていない。

**ベンチマーク結果**: 6シナリオ全てが基準値と完全に同一（失敗した荷物・
変位角度まで一致）。

**バグを疑って`only_001`をused_safe=True/Falseの発火トレース付きで
再実行し、切り分けた**:

```
DIAG_SAFE used_safe=True   × 16
DIAG_SAFE used_safe=False pool=10   ← 最後の1回だけ
item 22 not packable. removed.
```

**機構は正しく動作していた**（17回中16回、実際に安全な代替へ切り替えた）。
それでもfill_scoreが変化しなかったのは、序盤〜中盤の「安全な最良候補」が
たまたま元の最良候補と常に一致していたため状態遷移が変わらず、最終的に
詰んだ地点では**プール内の全アイテムに安全な置き場所が本当に存在しなかった
（真の手詰まり）**だったため。

これはSA・ブロック移動（一度も発火しない＝空振り）とは性質が異なる:
今回は**正しく発火した上で、たまたまローカル6シナリオの詰み方では
救えなかった**だけ。この変更はロジック上、既存の判断を安全な選択肢が
「ある時だけ」上書きするため、退行は理論的に起こり得ない。ローカルでは
測れないが、実機の（より多くの・異なる）評価シナリオでは中盤で詰む場面を
救える可能性があるため、ダウンサイドがほぼゼロの提出として採用する。

## 7. 実機提出結果: 安全優先は退行(24.407 → 25.043 → 24.935)、撤回

`require_safe`版を提出した結果、**24.934709 と実機では退行**した
(床ペナルティのみの25.043から-0.108)。「安全な選択肢がある時だけ
上書きするので理論上退行しない」という判断は誤りだった。

**何を見落としていたか**: この変更はオンラインポリシーの「今ステップで
どのアイテムを選ぶか」という競争条件を変える。安全性を要求すると、
あるアイテムの最良位置が使えなくなり、そのアイテムのスコアが相対的に
悪化し、**その結果として別のアイテムが選ばれる**。選ばれるアイテムが
変われば、その後の全ての状態遷移が変わる——これはこのセッションで
構築フェーズについて10回以上確認してきた「アイテム選択順序へのいかなる
摂動も連鎖的に予測不能な変化を生む」現象と、実は同じ構造だった。
「個々の配置判断は退行しない」という局所的な安全性の議論は、
「その判断が引き起こすアイテム選択の変化」という非局所的な影響を
見落としていた。

ローカル6シナリオで無変化だったのは「たまたまこの6シナリオでは
アイテム選択が変わらなかった」だけで、実機のより多様なシナリオでは
選択が変わり、cog_score/stability_score/placement_score/soft_item_score
（ローカルで測れない4項目）のいずれかを悪化させたと考えられる。

`git revert`で撤回済み（`f747c24`）。現在はPublic 25.043 の構成
（床ペナルティのみ、コミット`462d7c2`相当）に復帰。

**教訓**: 「ロジック上退行しえない」という主張は、それが本当に
「アイテム選択順序に影響しない」ことを意味する場合にのみ成立する。
オンラインポリシーであっても、複数アイテムの中から1つを選ぶ判断に
手を入れる変更は、構築フェーズのスコアリング変更と同じリスクを負う。
局所探索コストへの変更（cog/stabilityタイブレーク、SA、ブロック移動）が
安全だったのは、順序を選ぶのではなく既に決まった順序を検証済みの
コストで比較していたから。`require_safe`はこの安全な型から外れていた。
